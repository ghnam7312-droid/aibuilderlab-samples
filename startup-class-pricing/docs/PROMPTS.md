# 프롬프트 기록

> 1기 목표 모델 예시입니다. ‘만들 때 쓴 프롬프트’는 가상의 수강생이 COVI에서 썼다고 가정한 대표 예시이고, ‘서비스가 쓰는 지시문’은 [ai-task.json](ai-task.json)에 있는 서버용 원문입니다.

## 1. 만들 때 쓴 프롬프트 (대표 4개)

| 시기 | 목적 | 프롬프트 |
|---|---|---|
| 5주 | 계산 점검 | 1기 계산표야. 가격 69,000원에서 재료비, 배송비, 피드백 시간만 뺐어. 실제 정산이랑 안 맞는데 빠진 비용이 뭔지 같이 찾아 줘. |
| 5주 | 1인당 계산 | 가격, 플랫폼 수수료율, 결제 수수료율, 키트 원가, 배송비, 작가 시간(분)과 시간당 값을 받아서 1인당 남는 돈과 손익분기 인원을 계산하는 함수를 원 단위 정수로 만들어 줘. |
| 5주 | 사전 신청 | 가격 카드별 방문 수와 신청 수로 신청률, 방문자당 남는 돈, 예상 수강생, 예상 이익을 계산하고 방문자당 남는 돈이 큰 구성을 추천해 줘. |
| 5주 | 숫자 검사 | AI가 쓴 추천 이유에 입력에 없는 숫자가 있으면 버리는 함수를 만들어 줘. 9.9만, 12.5% 같은 표기도 입력 숫자로 인정하고, 10 이하 작은 수는 허용해. |

## 2. 서비스가 쓰는 지시문 (`classpricing.review`)

공통 꼬리말: `모든 문장은 한국어로, 짧고 구체적으로 쓴다. 반드시 JSON 하나만 출력하고 다른 말은 쓰지 않는다.`

```
온라인 클래스 운영자가 다음 기수의 가격·구성을 고르도록 돕는다. input.plans에는 구성별 가격,
수수료·재료비·작가 시간까지 뺀 1인당 남는 돈(net), 남는 비율(marginPct), 사전 신청 테스트의
방문·신청·신청률(convPct), 방문자당 남는 돈(perVisitor), 예상 수강생(students)과 예상
이익(profit)이 있다. pick은 plans의 id 중 하나. reasons는 고른 이유 2~3개, risks는 조심할 점
0~3개. 숫자는 input에 있는 숫자만 그대로 쓰고, 새로 계산하거나 시장 평균·경쟁 가격처럼 input에
없는 사실을 지어내지 않는다. 최종 결정은 운영자가 한다는 전제로, 단정하지 말고 근거를 보여 준다.
출력 형식: {"pick":"B","reasons":[""],"risks":[""]}
```
- 입력: `{ plans:[{id, name, price, net, marginPct, visits, signups, convPct, perVisitor, students, profit}], fixed, visitors }` · 최대 600토큰
- 화면 검사: `normalizeReview()` — pick이 있는 구성인지, 이유가 1개 이상인지, 이유·조심할 점의 숫자가 모두 입력에서 나온 숫자인지

## 3. 왜 이렇게 썼나

- **계산은 코드가, 말은 AI가.** 1기의 실수는 계산에서 나왔다. 그래서 수수료·남는 돈은 테스트가 있는 `logic.js`만 계산하고, AI에는 다 계산된 숫자를 준다.
- **새 숫자 금지.** “경쟁 클래스 평균 12만 원” 같은 그럴듯한 숫자가 들어오면 판단이 흔들린다. 지시문으로 막고, 화면에서 한 번 더 검사한다.

## 4. 실패했던 이전 버전

```
59,000원, 99,000원, 149,000원 세 구성 중 어떤 가격이 좋을까? 재료비는 18,000원이야.
```
- 결과: “149,000원 구성이 1인당 이익이 가장 크고, 비슷한 클래스 평균 가격대(약 12만 원)보다 높아 프리미엄 포지션이 가능합니다.”
- 문제: 수수료를 빼지 않은 이익으로 비교했고(1기와 같은 실수), 입력에 없는 ‘평균 가격’을 지어냈으며, 사전 신청 결과를 보지 않았다.
- 고친 점: 계산을 코드로 옮기고, 사전 신청 숫자를 함께 주고, 입력에 없는 숫자는 버리는 검사.
