## 5주차 전반 — 화면부터 말고, 화면이 쓰는 데이터부터

**한 일**
- 지난 학기 캡스톤에서 구조를 세 번 갈아엎은 이유를 적어 봤다. 세 번 모두 “화면을 만들다가 필요한 데이터가 생겨서” 테이블을 바꿨다.
- 이번에는 화면 7개(로그인, 스터디 목록·만들기·상세, 출석 체크, 과제 제출, 피드백)를 먼저 정하고, 화면마다 보여 주고 저장하는 데이터를 적었다.

**막힌 것 → 해결**
- 없음. 화면 목록을 팀원 3명과 30분 안에 합의한 것이 이번 주의 가장 큰 일이었다.

---

## 5주차 후반 — AI 제안 13개를 7개로

**한 일**
- 화면 목록을 주고 Claude에게 테이블 설계를 받았다. 13개가 나왔다: 필요한 7개 + 알림, 댓글, 좋아요, 태그, 스터디-태그 연결, 변경 이력.
- 화면 × 테이블 표를 만들어 화면마다 쓰는 테이블에 체크했다. 아무 화면도 쓰지 않는 6개가 보였다.
- **해결: 화면별 필요한 데이터만 남겨 7개로 축소.** 뺀 테이블마다 “어느 화면에서도 쓰지 않음 + 제안 용도”를 판단 기록으로 남겼다. 알림은 단톡방 공지로, 댓글은 제출의 피드백 칸 하나로 충분하다고 팀이 합의했다.

**막힌 것 → 해결**
- 처음 표대로 빼니 `users`가 빠짐 (화면에 ‘회원’이라고만 적어서) → 남은 테이블이 참조(FK)하는 테이블은 같이 남기도록 규칙을 바꿈. `likes`처럼 빠진 테이블(`comments`)을 참조하는 것은 같이 빠진다.

## 6주차 전반 — ERD와 API 14개

**한 일**
- 남은 7개 테이블의 컬럼, PK·FK, 개인정보 컬럼(이메일·이름)을 표시한 ERD.
- Claude가 처음 제안한 API 19개 중 뺀 테이블을 쓰는 5개(알림 목록, 댓글, 좋아요, 태그, 변경 이력)를 같이 뺐다. 14개가 남았다.
- API마다 어느 화면이 부르는지 적었다.

**막힌 것 → 해결**
- API 목록을 따로 관리하다가 테이블을 뺀 뒤에도 알림 API가 남아 있었음 → API에 쓰는 테이블을 적어 두고, 테이블이 빠지면 자동으로 걸러지게 함.

---

## 6주차 후반 — 판단을 남기는 설계서

**한 일**
- 리뷰 체크리스트: 모든 테이블을 쓰는 화면이 있다, FK 대상이 남아 있다, 화면마다 API가 있다, 이름은 snake_case 복수형. 개인정보 컬럼 접근과 팀원 확인은 사람이 체크한다.
- ‘그래도 남기기’는 이유를 적어야만 된다. 이유는 판단 기록에 그대로 남는다.
- 판단 근거 문장은 Claude(`techspec.reasons`)가 다듬되, 결정은 바꾸지 못하게 했다. 결정과 어긋난 문장은 버린다.
- 설계서 마크다운 내보내기, 로직 분리 + 테스트 11개.

**결과 (1기 목표치)**
- 테이블 7개 · API 14개 정의, 이후 구조 변경 0회
