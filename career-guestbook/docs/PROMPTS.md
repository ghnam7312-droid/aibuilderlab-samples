# 프롬프트 기록

> 1기 목표 모델 예시입니다. ‘만들 때 쓴 프롬프트’는 가상의 수강생이 COVI에서 썼다고 가정한 대표 예시이고, ‘서비스가 쓰는 지시문’은 지금 실제로 서버에서 돌아가는 원문입니다.

## 1. 만들 때 쓴 프롬프트 (대표 5개)

| 주차 | 목적 | 프롬프트 |
|---|---|---|
| 5 | 화면 뼈대 | 이름 없이 300자까지 쓰는 쪽지 모양 입력칸과, 남기면 벽에 붙는 쪽지 목록을 HTML/CSS/JS로 만들어 줘. 프레임워크 없이. |
| 6 | 규칙 분류 | 칭찬·개선 요청·질문·기타를 단어 사전으로 나누는 함수를 만들어 줘. 동점이면 질문 > 개선 요청 > 칭찬. ‘~었으면 좋겠어요’는 칭찬이 아니야. 테스트 케이스도. |
| 6 | 응답 검사 | Claude가 돌려준 JSON이 정해진 범주가 아니면 null을 돌려주는 검사 함수를 만들어 줘. 감정 값이 이상하면 중립으로. |
| 7 | 실시간 | 3초마다 `after=마지막 번호`로 새 글만 가져와 벽에 붙이는 폴링을 만들어 줘. 화면이 숨겨지면 느리게, 실패하면 간격을 늘려. |
| 8 | 디버깅 | 전체 화면에서 Esc를 누르면 진행 모드 클래스가 남아. fullscreenchange 이벤트로 같이 끄는 코드로 고쳐 줘. |

## 2. 서비스가 쓰는 지시문 (서버 `/api/demo/ai`)

공통 꼬리말: `모든 문장은 한국어로, 짧고 구체적으로 쓴다. 반드시 JSON 하나만 출력하고 다른 말은 쓰지 않는다.`

### guestbook.classify — 남길 때 한 건 분류
```
행사 익명 피드백 한 건을 분류한다. category는 칭찬, 개선 요청, 질문, 기타 중 하나.
sentiment는 긍정, 중립, 부정 중 하나. topic은 운영진이 손볼 영역을 2~6자로
(예: 시간 배분, 장소·시설, 음향·화면, 진행 방식, 음식, 안내·공지). reason은 판단 근거 한 문장.
출력 형식: {"category":"","sentiment":"","topic":"","reason":""}
```
- 입력: `{ text }` · 최대 200토큰
- 화면 검사: `normalizeClassify()` — 범주가 다르면 버리고 규칙 결과

### guestbook.summary — 운영진 요약
```
행사 피드백 목록을 운영진용으로 요약한다. lines는 3문장(전체 분위기, 가장 많은 의견, 바로 할 일).
actions는 개선 요청을 주제별로 묶은 것으로 많은 순서 최대 4개, suggestion은 다음 행사에서 할 구체적 조치.
출력 형식: {"lines":["","",""],"actions":[{"topic":"","count":0,"suggestion":""}]}
```
- 입력: 최근 80건, 글마다 200자까지 (`summaryInput()`) · 최대 600토큰
- 화면 검사: `normalizeSummary()` — 문장이 2개 미만이면 버리고 규칙 요약

## 3. 지시문을 고친 이유

| 버전 | 바꾼 것 | 이유 |
|---|---|---|
| v1 | “이 피드백 분류해 줘” | 매번 다른 이름의 범주가 나옴 |
| v2 | 범주 4개를 지정 | 앞뒤에 설명 문장이 붙어 JSON 파싱 실패 |
| v3 | 출력 형식 고정 + “JSON 하나만” + 화면 검사 | 파싱 실패가 사라지고, 이상한 값은 검사에서 걸러짐 |
